## Monorepo layout

This is a Bun workspaces monorepo. `apps/web` is a TanStack Start app (Vite + Nitro, file-based routing under `apps/web/src/routes`; `src/routeTree.gen.ts` is generated by the Vite plugin and committed).

- `apps/web` stays thin: routing, root layout/document and wiring only, with no feature code (prompts, config, business logic, Node APIs); oxlint bans `node:*`, the Copilot SDK and `@app/contracts` there. Routes compose features from `packages/features`. The only non-route files are `*-handlers.ts`, which just connect an adapter to a feature's server.
- `packages/features` and `packages/ui` must not import from `@tanstack/react-start`, `@tanstack/react-router` or any other web framework; the app only consumes them. `packages/ui` holds the styled ui-sdk wrappers, shared layout and Tailwind theme.
- `packages/features` holds one folder per feature. A feature can have a `client/` (React UI, entry `@app/features/<feature>/client`) and a `server/` (plain `(Request) => Response` endpoints, entry `@app/features/<feature>/server`). Client and server never import each other, and the server imports no React or components. The feature work happens here. Code that more than one feature needs lives in `packages/features/src/shared/{client,server}` (the JSON/SSE helpers for endpoints, the transcript export format, the client's `request` helper); the same import limits apply to it, and features do not import each other.
- Server state on the client goes through TanStack Query. `apps/web/src/router.tsx` creates the `QueryClient` (one per request) and `@tanstack/react-router-ssr-query` provides it; features use `@tanstack/react-query` hooks (`useMutation`, `useQuery`) and never create a client or provider. Other client state (selections, drafts, streams, view filters) lives in Zustand stores, one `*-store.ts` per page or flow in the feature's `client/`, built with `createStore` from `packages/features/src/shared/client/create-store.ts`: state only inside the store, actions as exported plain functions (never selected from the store), atomic selectors in components, and a `reset` that the page calls when it unmounts. Plain `useState` and `useReducer` are banned in features (oxlint `no-restricted-imports` on `react`, which also rejects `import React` and `import * as React`); keep DOM refs in `useRef` and external subscriptions in `useSyncExternalStore`. The sidebar in `packages/ui` keeps its open state in a per-provider store (`packages/ui/src/lib/sidebar-store.ts`), because a shared singleton would leak between server requests.
- `packages/contracts` holds types shared by client, server and adapters, including the `CaptionSource` port. `packages/teams-cdp` is an adapter that implements it over the Chrome DevTools Protocol; it must not import `@app/features`, `@app/ui`, React or a web framework (oxlint enforces this). The captions server must not import the adapter; the app wires it in `apps/web/src/caption-handlers.ts`.
- `packages/storage-sqlite` owns the one SQLite file (`openDatabase`, per-module `migrate`) and implements the `TranscriptStore`, `GraphStore`, `PipelineLog` and `SettingsStore` ports, and any future store, with the built-in `node:sqlite`, which both Node 22.13+ and Bun provide (the built server runs on Bun in `bun run start` and as the desktop sidecar; the Vite dev server runs on whichever runtime launches `vite`). It has the same import limits as `teams-cdp` (oxlint enforces them). Recording runs on the server (`captions/server/recorder.ts`), independent of any browser; the page only follows it. The meeting graph's vocabulary and rules live in `packages/contracts/src/graph-vocabulary.ts` and are described in `docs/graph-model.md`; change the rules there, never in an adapter.
- `packages/copilot-sdk` implements the chat (`GetChatStatus`, `CreateChatSession`) and `StructuredModel` ports with the GitHub Copilot SDK (same import limits as the other adapters, enforced by oxlint). The chat and graph servers must not import it; `apps/web/src/chat-handlers.ts` and `graph-handlers.ts` wire it. The SDK stays external in the production build (`apps/web/vite.config.ts`) because it resolves its runtime package at run time; it is a dependency of `apps/web` and of the root package.
- The meeting-graph pipeline is the `graph` feature (`packages/features/src/graph/server`, see `docs/graph-pipeline.md`). It follows recordings through the `RecordingObserver` port, which the captions recorder calls after saving each caption; the app passes the pipeline in (`apps/web/src/caption-handlers.ts`). It is off until the "Build graph live" switch is turned on (the `SettingsStore` port, kept by `packages/storage-sqlite`; the pipeline asks `enabled()` on every caption, which the graph feature answers from memory). The graph feature can also build a graph from a saved transcript on demand (`createGraphBuilder`, the "Generate graph" button): `apps/web/src/routes/transcripts.tsx` puts the graph feature's button into the transcripts page's `actions` slot, so the captions and graph features never import each other. A model only ever proposes changes: plain code checks quotes and statuses, and the store enforces the graph's rules. Shared stores are opened once in `apps/web/src/storage.ts`.
- `apps/desktop` is a Tauri shell with no UI of its own: it starts the built web server (`apps/web/.output`) as a bundled Bun sidecar and navigates its window to it. Keep the app a normal web server; the shell only supplies `PORT`, `HOST` and `TRANSCRIPTS_DB`. `scripts/prepare-sidecar.mjs` must install the packages the server build leaves external (currently `@github/copilot-sdk`). In `desktop:dev`, `src-tauri/tauri.dev.conf.json` sets `build.devUrl` to the Vite dev server (port 3100) and `lib.rs` starts no sidecar when `tauri::is_dev()` and a dev URL are both set; `desktop:dev:built` is the old sidecar run.
- Desktop updates: `packages/features/src/updates` talks to Tauri only through `window.__TAURI__` (no `@tauri-apps` import), so it is inert in a browser. The updater endpoint, public key and the `127.0.0.1` capability live in `apps/desktop/src-tauri`; the Desktop app workflow (`.github/workflows/desktop.yml`) signs builds, creates the release tag only after every build passes, and writes `latest.json`.
- ui-sdk (`@ui-sdk/react`, `@ui-sdk/core`): before using it, follow the ui-sdk skill if it is installed, and read `node_modules/@ui-sdk/react/docs/llms.txt`. To build a new component, also search `node_modules/@ui-sdk/react/docs/core.md` by heading, and read `rendering.md` next to it.
